# Extension API 1.0 — aex-1.3

The [requirements](EXTENSIONS-SPEC.md), [contract types](../Sources/ArchitectureExtensions/Contracts), and [JSON schemas](../Schemas) define the API. The supported host is macOS 27 with Swift 6.4.1. The root package does not depend on Invar, Formal, Web, Java, Lean or any verifier backend.

## Connection and authority

Providers are separately launched programs using `ArchitectureClient.ExtensionProviderClient`. Explorer never discovers or starts them. Unix peer PID/audit token and code identity come from the operating system, not JSON. The daemon pins its CLI binary and the paired Web binary generated by `Tools/build.py`. Arbitrary helpers do not gain host privilege. Headless builds omit the Web pairing. Rebuild/restart the daemon after replacing either binary.

1. Register a bounded `ExtensionManifest`, negotiating `extensionAPI.major=1`, `minimumMinor=0`, IR major 1 and `specificationProfiles` including `aex-1.3`.
2. The first call returns `APPROVAL_REQUIRED`. The authenticated Web Extensions panel shows the actual executable/hash and requested permissions. The user chooses permissions and approves.
3. The same live audit peer repeats registration and receives its credential. A subsequent process supplies the saved `resumeCredential` and must match the approved manifest/binary/code identity. Protect that credential as a secret.
4. Every call includes `extensionCredential` in the RPC envelope. Heartbeat/request activity renews a 15-second session. Reconnection creates a different session; old tokens, leases and staging authority do not transfer.

The approved scope is the selected whole workspace. Granular scope requests return `UNSUPPORTED_CAPABILITY`. Provider identity and namespaces are fixed by the grant. Permission expansion/manifest/version/binary changes require new approval. Permission reduction or disablement revokes sessions. A Provider cannot approve itself.

| `extensions.heartbeat` | Own session | Renew peer-bound session |
| Existing graph reads, `graph.scan`, `inputs.manifest` | `graph.read` | Fixed snapshot, bounded pages |
| `inputs.acquire/renew/release` | `graph.read` | Creating session owns the lease |
| `inputs.read`, `source.read` | `inputs.read` | Exact bytes vs bounded preview are distinct |
| `events.poll` | `events.subscribe` | Core epoch/sequence plus extension revision, origin and causation |

| `annotations.replaceBatch` | `annotations.write.own` | Stages a publication page |

Core graph MCP tools remain read-only. Canvas MCP tools operate on shared presentation sessions and expose no extension dispatch/approval. The HTTP read allowlist is separate from the POST mutation allowlist. POST requires the authenticated cookie, exact Origin and session CSRF bearer token obtained via authenticated `host.context`. Provider content cannot provide browser controls or markup.

## Fixed inputs

`inputs.manifest` returns `manifest` and its canonical `inputManifestDigest`. File digests cover original file bytes; the manifest digest covers the entire canonical InputManifest, including files, metadata/context, coverage and scope. `dependencyStatus=unknown` conservatively records incomplete dependency metadata. Byte equality alone does not prove external input applicability.

The SDK `verifiedInputs` captures a lease, reads all original files in bounded chunks and validates every file SHA-256 before returning the complete set. Historical captured bytes survive live disk edits; unavailable historical bytes fail rather than substituting current disk data. Release occurs on success and failure. Leases renew for at most 900 seconds from acquisition and never cross sessions/restarts.

## Atomic publication

```text
begin (before work): runID + scope + contributionSetID + binding + contributionKinds + viewIDs
  -> host generation + publicationID
prepare: immutable ID -> contribution SHA-256 manifest
stage: annotations.replaceBatch / extensionGraphs.replace / views.replace
commit: exact manifestDigest + completion
  -> one Store transaction updates all contributions and the slot head
```

`runID` is the Provider-local ID at begin; subsequent calls use the returned namespaced `id`. `completion=complete` means the declared output is complete, never that a proof succeeded. Failed/partial/cancelled/unknown attempts preserve the previous complete head. A complete empty manifest can replace it with empty results. A late older generation returns `PUBLICATION_SUPERSEDED` with `historySaved=false` in the diagnostic and cannot roll the head back. Retry with identical manifest digest returns the same committed result. Finished attempts cannot be reopened; a new attempt uses a new ID.

Reauthorized begin for an uncommitted run retains its generation but issues a new publication ID and discards old staging. The fixed binding and declared contribution kinds/view IDs must match. Core EntityID/FactID values remain source identities, never matched by display name. External graphs retain their own namespace and are not joined into core edges.

`extensions.view` pages at 3 MiB without splitting a publication. `nextCursor` is tied to snapshot and extension revision; changes produce `CURSOR_EXPIRED` and require resync. A selected export contains its bounded publication page with explicit `truncated/nextCursor`; offline actions are disabled and no source/artifact requests are made.

## Actions, receipts and recovery

Every external forwarded operation uses effect `externalExecution` and host confirmation, including manifests that set `requiresConfirmation=false`. Ordinary host navigation/read operations do not receive execution tokens.

`actions.prepare` validates registered schema arguments and binds the exact action definition, Provider/session, selection, snapshot/manifest and deadline. The UI shows the executable, inputs, arguments and fingerprint. `actions.confirm` consumes the token and reserves dispatch atomically before `actions.next` may deliver it. Unknown delivery is never automatically delivered again.

The fingerprint is SHA-256 of sorted-key `CanonicalJSON` over request ID, stable Provider ID, action ID/definition digest/schema/effect, complete binding, typed arguments and deadline. Session, registration, token and transport IDs are not fingerprint fields; they remain independently checked authorization bindings. Deadline is host-issued, five minutes after preparation; retention is deadline plus 3600 seconds.

The Provider calls `ProviderActionLedger.reserve` before starting work. Only `mayStart=true` permits a start. Duplicate/conflicting requests, lost ACKs, restart, ledger loss and expiry have distinct outcomes. The same request always retains its initial `ActionReceipt`; job state is a separate monotonically revised stream. Reconciliation uses the side-effect-free `lookup` method; a missing record returns `ACTION_OUTCOME_UNKNOWN`. It may restore the old receipt under a newly authenticated session, and never creates new work from unknown delivery.

Cancel is another registered action with `operation=cancel` and typed original `requestID/jobID/runID` arguments. Confirmation rechecks that target. Receipt means acceptance, not stopped work. The original job remains `cancelling` until the Provider reports terminal cleanup completion. Normal completion wins if it already occurred. Terminal states never change to a different terminal state; old revisions are ignored.

## Declarative views and artifacts

Supported kinds are text, table, keyValue, artifactList, graph, timeline and overlay. Their bounded payload shape is enforced by `ExtensionRules`. Text remains literal, including HTML/JS-looking strings. Graph edges and unknown external attributes retain their supplied meaning; no temporal or proof semantics are inferred.

Artifact entries are workspace-relative references with SHA-256. The renderer displays reference metadata only: it does not open files, follow symlinks or fetch arbitrary URLs. Source navigation is a host control to the exact recorded snapshot/entity. Source bodies, arbitrary artifact contents and secrets are not bundled in exports.

## Node menus

A Provider contributes to a live source node through a published `ExtensionContribution`. Include its exact entity ID in `binding.entityIDs` for the captured workspace, snapshot and input manifest. The host projects current bound results into the node header menu. One publication can target multiple nodes. Empty entity bindings and fact-only bindings supply no node menu entries.

| Published kind | Node menu behavior |
|---|---|
| Graph or registered graph view | Open the published graph in the shared Canvas. Formal metadata selects the diagram presentation. |
| Annotation | Read the reported claim, status, scope and assumptions. |
| Registered view | Read the declared table, timeline, overlay, text, key/value data or artifact references. |

Model verification opens a condition from the node-bound verification annotation. Each condition identifies its original evidence bundle and claim and supplies its checked entry, authored clauses, backend, outcome and translation scope. The initial Canvas projects only that claim and its relationships. The selector exposes other conditions and the original model graphs. When a publication contains only structural models, Verify model opens the first supported graph and the selector lists the others.

A condition can carry ordered Swift parameter names and syntax-backed candidate call sites from the checked source snapshot. Explorer reads only the selected call range using the file entity and snapshot, verifies its path, digest and UTF-8 bounds, and associates the argument expressions by position. The graph retains the original claim and distinguishes source observations from proof of the generated model. Direct conditional calls are presented first.

The menu uses literal published titles or declaration IDs, records their Provider, and retains publication and contribution identities when opening a result. Workspace model browsing continues to use formal graphs independently of entity selection. Node menu entries consume the existing read and publication contracts. Executable Provider actions retain their separate confirmation flow.

## Budgets and backpressure

| Owner | Limit |
|---|---|
| Host extension state | 16 MiB, 16 grants, 64 pending approvals/confirmations/sessions |
| Host per session | 64 admitted requests per second; typed `RESOURCE_LIMIT` |
| Client credential instance | 32 calls/second; shared actor across value copies; 64 pending calls |
| Dispatch ledger | 512 records until deadline + 3600 seconds; no unexpired eviction |
| Provider ledger | 512 records / 1 MiB, process-locked atomic file |
| Run records | 128 retained runs; no ID reuse/eviction; explicit exhaustion |
| Manifest / views | 64 KiB / 16 declared views and actions |
| Contribution / publication | 1 MiB / 2 MiB, at most 64 contributions |
| Partial graph | 500 nodes / 1500 edges |
| Public response | 3 MiB pages, indivisible publications |
| Inputs | Existing snapshot owner: 4 leases/captures, 256 MiB content, 256 KiB chunks |

`RESOURCE_BUSY` indicates a competing persistence operation and guarantees no publication/dispatch side effect for that rejected request. The daemon reserves 16 of 64 connection tasks for paired host clients, limiting idle non-host connections to 48. Event updates carry the current extension sequence and explicit `extensionResyncRequired`; a skipped revision requires a full public-view resync. Core changes keep `category=structure` and `originProviderID=host`; the separate `extensionEvent` preserves the last external origin without masking source changes. Annotations do not mutate the core snapshot sequence, and Provider consumers can filter `originProviderID/category` to prevent feedback loops.

## Development refactoring policy

Only the current `aex-1.3` contract is supported. Removed profiles, per-record mutation APIs, snapshot lease aliases and old cache formats are rejected. There are no adapters or separate annotation/graph write stores. All current external results come from atomic run contributions. A complete replacement omitting an ID removes it from current results while retaining the prior completed run as history.

Cache format 2.0 uses a dedicated extension_state document. Older caches are explicitly rejected without modification or migration; archive a development cache and rebuild it. The source workspace is never changed. `graph.annotations` and `extensionGraphs.list` return paged `items` envelopes containing the contribution, Provider/run/publication identity and applicability from committed heads.

## Canvas integration
Providers may request `canvas.read` for Canvas list/get/export and both `canvas.read` and `canvas.control` for presentation mutations, which return acknowledged session data. Existing grants do not imply these permissions. Imported/session data is separate from source snapshots and committed verification results. See [Canvas formats and commands](CANVAS-FORMATS.md).

### Node model execution
The host-owned node options menu uses the registered invar.verify-model.v2 action with one entity and an optional indexed property path in the displayed source snapshot. The host shows the prepared provider executable, arguments, binding and request fingerprint before forwarding the confirmed action. Dispatch status and model evidence are shown on that entity. Defining conditions opens a separate thread-bound annotation.

A provider may include an optional plain-text `attemptDiagnostic` in the publication manifest (1–1024 UTF-8 bytes). A terminal incomplete run exposes it as `attempts[].diagnostic` only for the bound snapshot. The diagnostic has no effect on the slot head.

Opening model verification presents the current committed TLA+ or Lean graph for the selected provider, node and exact input on the Canvas. Execution confirmation remains separate. A confirmed request follows its own dispatch to its run and committed publication, including when completion precedes publication. Other requests and verification summary graphs cannot replace the displayed model. Closing the review or navigating away ends local result following.

A large formal diagram initially frames a declared root and its nearest connected node. Fit retains its full-diagram meaning, and returning to an open session restores its saved camera.

With no indexed conditions, the node menu presents the generation intent for the pinned implementation. Clicking Verify model confirms this source-only action or reopens its published draft. The two emitter graphs remain labeled Unverified when reopened as standalone Canvas sessions.


### Node accessories

An annotation can supply `attributes.nodeAccessory` to customize the trailing header slot of its bound source nodes. The value is an object with three string fields.

| Field | Accepted values |
|---|---|
| `icon` | `info`, `flag`, `bookmark` |
| `tone` | `neutral`, `accent` |
| `label` | Nonblank plain-text command label, at most 80 UTF-16 code units |

The host draws the glyph inside the node at graph scale. A transparent native button at the same slot provides pointer and keyboard access, with the exact reported result as its accessible label. Selecting it opens the originating annotation. The node menu exposes the same labeled command. Multiple accessories share a count and a chooser. An invalid accessory contributes no mark. Node accessories use the annotation's existing publication and binding permissions. Verification conditions contribute host-defined outcome marks to the same slot.
